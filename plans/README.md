## Findings considered and rejected

Measured and rejected (don't re-audit):

- **`ws` sprint re-entry (plan 003)**: measured by executor 2026-08-07 with
  behavior-verified standalone variants — case 1 (200-char, escape at idx 5):
  341 → 159 ns; case 3 (30-char, one escape): 48.4 → 37.3 ns; case 4 (clean,
  native path): unchanged; case 5 (quote-dense `'"a'.repeat(60)`): 286 →
  366 ns (+28%). The outer-loop re-entry bookkeeping is paid per special
  char, so dense-escape strings lose. Current bail-once design stays.

- **2-digit pair-table itoa for int32**: 5.52 vs 5.40 ns/op — JSC's integer
  div/mod is already cheap; no win.
- **High/low-split itoa for 53-bit integers** (avoid `''+n` for timestamps):
  59.9 vs 54.4 ns/op — the `Math.floor`-division split loses to `''+n`;
  Plan 002's loop-copy captures the recoverable part (the native-write
  overhead) instead.

By-design, not findings (deliberate measured decisions recorded in the
session that produced this encoder — do not "fix"):

- No per-chunk capacity checks / whole-encode retry on overflow (OOB
  typed-array stores are silent no-ops; single end check).
- `ws`/`wn` as shared module functions rather than inlined per-encoder code
  (one JIT copy across all encoders).
- 40-char `stringWriteThreshold` for the native-write fast path (measured
  crossover vs the 0.45 ns/char JS loop against 15–19 ns native-call cost).
- `esc` regex including `\ud800-\udfff` so surrogate-bearing strings take the
  JS loop (native write would emit U+FFFD; JSON.stringify escapes lone
  surrogates).
- `TextEncoder.encodeInto` anywhere: measured 37 ns, always loses to
  `buf.write`.
- Per-element itoa for number arrays instead of `arr.toString()` + write
  (already implemented; 2.3× faster).
